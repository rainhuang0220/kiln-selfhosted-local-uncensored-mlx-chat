# 推理说明（mlx-lm 0.31.3）

针对这台机器上的 **Qwen3.8-27B 4bit 混合架构**。没测过的不要写成「已经优化了」。

## 硬件账

| | |
|---|---|
| 芯片 | Apple M4 |
| 统一内存 | 24 GB |
| Metal 建议工作集 | 约 **17.8 GB** |
| 模型权重 | 约 **14.1 GB** |
| 剩下给激活 + 缓存 | 大约 **3.7 GB** |

模型卡写「建议 32GB+」是有原因的。24GB 能跑，但余量很小。

这是混合结构：64 层里 48 层线性注意力（Gated DeltaNet）+ 16 层全注意力。线性层的 cache（`ArraysCache`）**不能裁剪**。投机解码、把「更长的旧缓存剪成公共前缀」都要求整层可裁，所以这两项在这颗模型上**做不了**。

## 能用 / 不能用

| 能力 | HTTP 服务（Kiln 用的） | 仅命令行 |
|---|---|---|
| 跨请求前缀缓存 LRU | **能**，看 `cached_tokens` | `chat` 是另一套内存缓存 |
| `--kv-bits`（KV 量化） | **没有这个参数** | `generate` / `cache_prompt` 才有，且只能量化 16 层全注意力 |
| `--draft-model` 投机解码 | 参数在，**对这颗模型会报错** | 同样报错 |
| `--prompt-cache-file` 存盘 | 没有 | 有 |
| 把 262144 当可用窗口 | 不要 | 不要 |

## 前缀缓存怎么理解

服务进程里有一个全局 LRU。每次请求仍要送完整历史，server 按 **token 序列**找最长公共前缀。

- 命中会在 `usage.prompt_tokens_details.cached_tokens` 里出现
- 改 system、改 `enable_thinking`、改 `reasoning_effort` 都会导致前缀对不上，缓存作废
- 我们实测第二次相同请求：`cached_tokens = 111 / 112`

混合 cache 命中时会 **deepcopy** 一整份，所以 LRU 份数不能多。启动脚本用 `--prompt-cache-size 3 --prompt-cache-bytes 1G`，不要用默认 10。

## 启动参数（`npm run start:mlx`）

```text
--host 127.0.0.1 --port 8081
--decode-concurrency 1
--prompt-concurrency 1
--prefill-step-size 512
--prompt-cache-size 3
--prompt-cache-bytes 1G
```

`--decode-concurrency` 默认是 32，在 24GB 上等于自杀。并发 1 是必需，不是可选项。

Python 必须 **3.12**。3.14 会 OpenMP abort。

## 速度

24GB 上这颗稠密 27B 4bit，现场三次 A 的解码平均 **6.63 tok/s**（预热后；见 `BENCHMARK.zh.md`）。1k 输入的编码/prefill 约 **62 tok/s**。受内存带宽限制，不受信道路径限制。改旗标主要是防 OOM、稳 TTFT，**不能把 6.6 变成 30**。流式输出不是加速。

[MTPLX](https://github.com/youssofal/MTPLX) 用模型自带 MTP 头做投机解码，宣传 2–3×。对本目录无效：量化时 MTP 权重已经没了，mlx-lm 加载时也会丢掉 `mtp.*`。官方 27B Optimized Speed 峰值 25 GiB，这台 24GB 装不下。同机实测能过 30 tok/s 的是 **Qwen3.5-4B MTPLX**（解码约 52 tok/s）；9B 约 24 tok/s。启动：`npm run start:mtplx`，Kiln 侧 `MLX_BASE_URL=http://127.0.0.1:8082`。
